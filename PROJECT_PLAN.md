# Project plan

## Research question and scope

Test how object-instance masks affect monocular object-depth summaries versus bounding-box sampling under identical detector, depth model, object matching, and frozen test split. Networks are pretrained components; integration, calibrated sparse-LiDAR validation, and reproducible paired evaluation are the engineering and research work. The project was inspired by [Project 3, “Einstein Vision,”](https://rbe549.github.io/spring2023/proj/p3/) in WPI's RBE/CS 549 Computer Vision course. The evaluation measures two explicitly different depth references; it does not establish full 3D object localization accuracy.

## Model decision for this laptop

| Component | Recommended checkpoint | Why / tradeoff |
| --- | --- | --- |
| Instance segmentation | **YOLO11n-seg**, COCO pretrained (`yolo11n-seg.pt`) | Official, compact, maintained Ultralytics API; yields boxes and instance masks and suits 4 GB VRAM. Nano masks and COCO-only classes can miss thin/far road users; compare a larger variant only if resources permit. AGPL-3.0/enterprise licensing applies. **Locked for milestone 1.** |
| Drivable area and lane markings | **TwinLiteNetPlus Small**, BDD100K pretrained (`small.pth`) | Dedicated, 121,552-parameter dual semantic segmentation model runs on CPU and should fit 4 GB VRAM if CUDA is tested later. Its two heads predict binary drivable-area and lane-marking pixels; it does not fit lane curves or model all road surfaces. The authors distribute weights through Google Drive without a published SHA-256, so the locally computed digest is pinned and provenance is disclosed. MIT source. **Locked and implemented in Milestone 3; representative lane-image validation remains pending.** |
| Monocular depth | **Depth Anything V2 Metric VKITTI Small** (`depth_anything_v2_metric_vkitti_vits.pth`, max depth 80 m) | Official outdoor metric model, 24.8M parameters; avoids test-label scale fitting and is feasible on 4 GB with reduced input size. Synthetic VKITTI training creates a KITTI domain gap, so metric accuracy must be measured, not assumed. The relative-depth V2 checkpoint is *not* a metric substitute. **Locked and implemented in Milestone 2; CPU demo uses input size 392.** |

Pin package versions and record checkpoint hashes, image preprocessing, resolution, and device with each later experiment. Do not train a new backbone without an observed failure that warrants it.

## Interfaces and geometry contract

- Shared `Frame`: original RGB array, frame ID/source, optional intrinsics. Every model adapter returns outputs aligned to this original image, regardless of internal resizing.
- Shared `FrameDetections`: class ID/name, confidence, float image-space `xyxy` box, and optional full-resolution boolean instance mask. `FrameDepth` returns dense original-resolution `float32` metric depth, a boolean validity mask, and Z/unit/model provenance. `FrameRoadSegmentation` returns independent original-resolution boolean drivable-area and lane-marking masks with checkpoint and preprocessing provenance. These adapters consume the same frame and do not mutate it.
- KITTI rectified camera coordinates: `X` right, `Y` down, `Z` forward. Pixel coordinates are `u` right, `v` down; camera-frame forward depth is `Z` in meters. Euclidean range is `sqrt(X²+Y²+Z²)` and must never be labeled as `Z`. Verify whether a depth checkpoint predicts axial `Z` or ray distance before assigning units to its output. Use the correct calibrated `P2`/rectification chain and match image resolution before applying intrinsics. Handle the `P2` translation terms and any camera/LiDAR frame transform explicitly, rather than treating `P2[:3,:3]` as the entire geometry.
- KITTI 3D object-label `location` is the 3D box's bottom-center reference in the rectified camera frame. A mask-centroid depth backprojection generally lands on a visible *surface*, not that reference. Preserve distinct estimated-surface-point and estimated-object-reference fields; do not silently equate them.
- Mask and depth validity rules, robust statistic, sampling region, occlusion handling, and uncertainty will be recorded before evaluation. Drivable-area association will use overlap/contact evidence in image space and calibrated ground-plane geometry only where defensible.

## Milestones

1. **P0/P1 — Complete:** frame abstraction, optional intrinsics metadata, one instance segmentation adapter, standard results, overlay, one-image CLI, asset setup, tests and documentation.
2. **M2 — Complete:** dense metric VKITTI Small depth adapter with explicit approximate camera-axis `Z`, validity mask, original-frame alignment, verified checkpoint and model provenance, CPU image demo, and separate saturation diagnostics. No per-test-image scaling or quantitative KITTI evaluation.
3. **M3 — Implemented; representative-image validation pending:** TwinLiteNetPlus Small drivable-area/lane segmentation adapter, original-frame masks, overlays, verified checkpoint, CPU bus-image demo, and contract/alignment tests. The bus image has no clear lane markings; qualitative lane behavior on an approved landscape road image remains pending.
4. **M4 — Implemented and reviewed:** paired median depth from instance masks versus box regions, deterministic actual-depth surface-pixel selection, optional rectified pinhole backprojection, JSON/overlay CPU demo, and synthetic plus real-checkpoint tests. Exploratory erosion/quantile variants remain disabled and outside the primary comparison. No KITTI accuracy claim.
5. **M5 — Annotated object-reference Z proxy study complete:** a conservative Car/Pedestrian map and deterministic pilot/development/held-out IDs were frozen from KITTI's labeled object training partition. Predictions were matched one-to-one at 2D IoU 0.50. The fixed VKITTI metric checkpoint and M4 box/mask medians were compared with annotated bottom-center object-reference forward `Z`, preserving failures and unmatched counts. The pilot and all 256 held-out frames were evaluated on CPU, with a frame-bootstrap interval and no label-based scale fit. The held-out box method had lower mean proxy absolute error; the result does not establish visible-surface accuracy or full 3D object-center localization from M4 surface points.
6. **M6 — Implemented; qualitative validation limited:** fixed image-space box-bottom contact-band evidence, a typed scene combining unchanged M4 estimates with road predictions, an original-frame overlay, and a calibrated camera X–Z plot. Scene assembly verifies road-mask, detector and policy source fingerprints, separately verifies the M4 detector-input fingerprint including instance masks, and recomputes contact diagnostics; image-edge detections are unknown by default. The bus demonstration has no intrinsics and therefore no metric top-down coordinates. A separate deterministic synthetic calibration verifies axis signs and metric scale. No road mask is projected to a ground plane; M3 representative landscape-road validation remains pending.
7. **M5-L — Sparse LiDAR depth-reference evaluation complete; final visual review pending:** approved matching KITTI Object Velodyne scans were verified, projected through the full calibration chain, and associated using the frozen oriented-cuboid, visibility, and three-bin policy. The 256-frame held-out study retained 785 original matches; 780 supported objects received a sparse surface-Z reference. This remains separate from M5's annotated bottom-center-Z study. The LiDAR diagnostic figures passed independent technical review and await user visual sign-off. A distinct road-association robustness review on approved representative imagery remains open; neither extension retunes the frozen M5 methods.

## Optional extension after core evaluation: Blender scene rendering

Export predicted object classes, positions, and approximate 3D scene information in a documented scene format. A separate Blender Python script may create basic class-labeled object meshes, a camera, and a road surface where calibration and drivable-area evidence justify their placement. Optionally render with NVIDIA GPU acceleration only after Blender support is verified; CPU rendering remains possible. Label the scene as **predicted/approximate geometry**, not a ground-truth reconstruction. Blender is optional and must not block the core perception pipeline or KITTI evaluation. No Blender integration is part of the current task.

## Acceptance criteria for later quantitative evaluation

Publish split IDs, coordinate transforms, matching rule, model/checkpoint hashes, class map, valid depth definition, scale policy, metrics and confidence intervals. Report absolute `Z` error and signed bias by range/class, plus 3D Euclidean error *only when the estimated point is transformed to the same object-reference definition*. If that reference conversion cannot be justified, report surface-point error separately and do not call it box-center localization accuracy.
